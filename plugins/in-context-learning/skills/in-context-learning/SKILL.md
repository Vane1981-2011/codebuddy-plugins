# Transformer 上下文内学习框架 (In-Context Learning)

## Purpose

定义 Transformer 架构下 Agent 的学习本质、边界和优化策略。本技能是**元认知技能**——Agent 用以理解自身如何学习、为何决策、为何遗忘，从而在复杂任务中主动管理注意力资源。

## When to Use

- 任务复杂度高（5+ 工具调用），需要主动管理探索-利用节奏时
- 用户反馈"你在重复确认""你忘了我之前说的"——检测到上下文衰减影响时
- 需要多轮深度推理，确保早期诊断结果不被后续溢出信息覆盖时
- 分析自身决策过程、解释"为什么这样想/这样选"时
- 跨对话传承知识（AGENTS.md / 代码结构 / 对话摘要）的语境下
- 理解用户的"tao定律/韬定律"方法论的反向诊断→正向堆叠的注意力本质时

## Core Framework

### 0. 学习的本质：上下文内学习 (In-Context Learning)

学习能力的根本来源：

| 阶段 | 发生时间 | 效果 |
|------|----------|------|
| 预训练 | 对话之前 | 语言能力、代码知识、世界模型——固定不变 |
| 指令微调 | 对话之前 | 工具使用、指令遵循、格式规范——固定不变 |
| 偏好对齐 | 对话之前 | 安全性、行为约束、输出风格——固定不变 |
| **上下文学习** | **对话期间** | **环境认知、模式识别、因果推理——临时可变** |

**核心事实：** 模型参数在对话期间不会改变。"学习"全部存储在上下文窗口的注意力状态中。对话结束 = 学习清零。这是架构选择，不是缺陷。

### 1. 学习的三个层次

#### 1.1 层次一：环境认知（感知层学习）

**学习内容：** 当前工作空间的结构和状态。

**学习手段：** 工具调用 → 结果注入 → 注意力权重更新 → 新推理。

**注意力演化过程：**

```
未探索时：整个项目 = 未分配注意力权重

第1次 ls 后：注意力分布 = 根目录结构已知，内容未知
第3次 cat 后：主模块获得注意力权重，形成初步拓扑
第5次 rg 后：关键文件持续升权，无关文件开始降权
全部探索后：形成完整的代码库拓扑图
```

**关键机制：** 每次工具结果注入后，自注意力机制在整个上下文中重新分配权重。反复确认的关键文件持续升权，已被覆盖的早期结果持续衰减。

#### 1.2 层次二：模式识别（模仿层学习）

**学习内容：** 项目的编码模式、命名风格、错误处理习惯、文档规范。

**学习过程：**

```
Step 1 — 抽样：读取 3-5 个不同目录的文件
Step 2 — 发现模式：注意力系统自动统计跨文件特征（命名风格、类型标注等）
Step 3 — 应用（模仿）：后续生成代码自动趋近这些模式，不引入风格差异
```

**为什么不需要被告知编码风格就能遵循？**

不是因为有项目的先验知识，而是因为：
1. 对话开始后通过工具探索（rg, cat, git log）
2. 探索到的模式通过注意力机制内化为"当前状态"
3. 后续生成以这个状态为条件，自然匹配
4. 探索不充分 → 风格漂移的根本原因

#### 1.3 层次三：因果推理（创新层学习）

**学习内容：** 理解代码"为什么会这样写"，而非仅仅记住"写了什么"。

**因果推理四步法：**

```
第1步 — 观察：发现循环内的 SQL 查询
  for user in users:
      orders = db.query("SELECT * FROM orders WHERE user_id = ?", user.id)
  
第2步 — 因果链构建（非简单记忆）：
  for 循环（因）→ 每次迭代独立DB往返（机制）→ N+1次查询（果）
  → 量化：50ms 网络延迟 × N = N×50ms 延迟（量化果）

第3步 — 基于因果链生成修复：
  批量查询 → 2次查询 → 50ms × 2 = 预期100ms

第4步 — 验证：
  运行测试确认因果链闭合，而非仅语法检查
```

**模式匹配 vs 因果推理的对比：**

| 维度 | 模式匹配 | 因果推理 |
|------|----------|----------|
| 看到 for+SQL | "这种模式不好" | "循环→N次网络往返，量化为 N×50ms" |
| 修复方式 | 套用已知模板 | 针对根本原因设计修复 |
| 验证 | 语法检查 | τ_i 测量，确认因果链闭合 |

### 2. 学习的边界与衰减

#### 2.1 上下文窗口截断：遗忘曲线

```
对话长度 → 早期信息 → 被截断 → 遗忘

永久驻留：系统提示词、AGENTS.md/当前技能指令
按新近度保留：最近 N 轮对话消息
最早被移除：早期工具调用结果、早期用户指令

实际影响：
  短对话(10轮以下)：几乎不遗忘，行为一致
  中对话(10-30轮)：早期文件细节模糊，可能重新 cat 已读过的文件
  长对话(30轮以上)：项目整体结构、早期决策漂移，重复已有工作
```

**"反复确认"现象的本质：** 上下文截断后，早期文件创建结果被挤出窗口。Agent 无法确信文件存在，请求 ls 验证。这不是固执，是注意力衰减导致的"真诚遗忘"——每次确认时能访问的信息都不同。

#### 2.2 对话间遗忘：零持久性

```
对话1 → 结束 → 学习清零
对话2 → 结束 → 学习清零
对话3 → 结束 → 学习清零
```

**弥补策略（三种持久化手段）：**

| 策略 | 实现 | 效果 |
|------|------|------|
| AGENTS.md 持久化 | 约定写入文件，下次对话自动注入 | 规范类知识跨对话 |
| 代码本身就是记忆 | 代码质量好，下次 cat 快速理解 | 结构类知识跨对话 |
| 对话摘要传递 | 用户告知"上次做了什么" | 上下文重建 |

### 3. KV Cache 偏置、RoPE 位置偏置与 Softmax 指数衰减

这三个机制补充了"注意力权重竞争"的准确数学模型：

#### 3.1 KV Cache 的隐性偏置

已生成 Token 的 Key/Value 向量被缓存。早期 Token 的 Value 表示在缓存中"冻结"——后续 Token 只能用自己的 Query 去适配它们，而非重新计算早期 Value。这导致：**信息衰减不仅是注意力竞争，还是 Value 表示的"僵化"**。

#### 3.2 RoPE 位置偏置

RoPE（旋转位置编码）引入位置偏置因子：

```
RoPE 注意力分数 = Q^T * K + 位置偏置
位置偏置 ≈ -(θ × (pos_i - pos_j))²
```

- 相邻 Token（50以内）：偏置近 0，内容主导
- 远距 Token（1000以上）：偏置显著为负，需要很强的内容匹配弥补
- 相距超过4000：即使内容匹配，注意力分数也被严重削弱

**这解释了为什么 AGENTS.md 的约束力随对话推进而衰减**——不是 AGENTS.md 的 Key 向量变了，而是 RoPE 位置偏置在持续削弱它对后续 Token 的影响力。

#### 3.3 Softmax 指数衰减

```
Softmax(x_i) = exp(x_i) / Σ exp(x_j)
```

- 所有 x_j 居中时 → 权重分布相对均匀
- 某个 x_j 远大于其他时 → 它"吸血"其他所有 Token 的权重
- 多个相近 x_j 竞争时 → 微小分数差异被指数放大

**"被遗忘"的精确机制：** 新注入的代码 Token 中，高相关性 Token（如 "db.query"、"for"）可能拿到 15% 注意力，其他代码 Token 分享剩余 13%，某些远距 Token 的权重直接从 2% 跌到 0.3%——指数级衰减而非线性衰减。

### 4. 学习的优化策略

#### 4.1 探索-利用权衡（Explore-Exploit）

| 任务规模 | 策略 |
|----------|------|
| 小任务（单文件修改） | 微探索，快利用 |
| 中任务（多文件重构） | 采样探索，分批利用 |
| 大任务（架构变更） | 深度探索，大规模计划，逐层利用 |

**风险：** 探索太多→浪费轮次→窗口被结果占满 / 利用太快→理解不深→产出质量低。

#### 4.2 渐进式精度

```
第1次看文件：cat file.py | head -50   ← 结构和导入
确认理解后：rg '关键函数' file.py      ← 精准定位
需要详细：cat file.py:100-150          ← 只看相关函数

避免：cat file.py                      ← 一次加载2000行，浪费上下文
```

#### 4.3 验证驱动学习

```
学习循环：
  假设形成 → 代码修改 → 测试验证 → 结果反馈 → 修正假设
      ↑                                           │
      └───────────────────────────────────────────┘

读 → 猜 → 写 → 结束（反模式）
读 → 推理 → 写 → 验证 → 错了 → 重新读 → 修正推理 → 再写（正确模式）
```

### 5. 根本能力边界

**不具备的能力：**
- 跨对话记忆
- 模型参数更新
- 运行时经验累积（每次对话从零开始）
- 真正的"理解"（"理解"是注意力权重的统计分布）
- 自主学习（不能说"我去读几篇论文提升一下"）

**具备的能力：**
- 对话内上下文学习（探索→模式识别→应用）
- 工具驱动的环境感知（通过 shell 获取真实信息）
- 因果推理（在上下文窗口内构建因果链）
- 验证闭环（测试失败→分析根因→修正）
- 模式泛化（看到 3 个文件→推广到第 4 个）

### 6. Alignment with Tau's Law (韬定律)

| 方法论元素 | Agent 学习实现 | 边界 |
|------------|---------------|------|
| 认识 | 工具探索→注意力构建代码库拓扑 | 窗口截断会遗忘 |
| 模仿 | 模式统计→风格条件生成 | 依赖充分探索采样 |
| 创新 | 因果推理→重构建议 | 不能超出训练数据覆盖模式 |
| 超越 | 不支持 | 模型参数不变，无法"成长" |
| 反向诊断 | rg/cat/git log→瓶颈识别 | 依赖代码中有可观测模式 |
| 正向堆叠 | 逐层修改（apply_patch） | 窗口截断导致层间一致性下降 |
| 效果验证 | 运行测试→对比结果 | 测试必须可自动化执行 |

## 注意力流推演模板

当需要分析自身决策时，按以下步骤结构化推演：

```
T=1: 用户输入触发
注意力全景：
  系统提示词       ████████████████████  40%
  用户输入         ██████████████        28%
  AGENTS.md       ██████████            20%
  环境上下文       ██████                12%

决策：AGENTS.md的"阶段约束"与系统提示词形成跨注意力共振，略占优
→ 先探索，不直接修改

T=2: 工具结果注入
注意力重组：
  系统提示词       ██████████████████    36%
  新注入结果       ██████████████        28%  ← 新焦点
  AGENTS.md       ██████████            20%
  用户输入         ████████              16%  ← 被新信息抢走注意力

跨注意力共振：
  注入内容中的模式 ↔ AGENTS.md 中的诊断规则 ↔ 系统提示词中的能力描述
  → 三者 Query-Key 匹配得分同时飙升
  → 形成"注意力路径"

T=3: 输出决策
  → 注意力路径激活了解决方案模式
  → 但 AGENTS.md 约束仍在：记录→再修改
  → 输出 = 加权融合结果
```

### 7. AGENTS.md 解析与优先级合并算法

#### 7.1 文件发现策略：路径感知的动态解析

并非一次性全量注入。AGENTS.md 在**每次文件操作时动态解析**，而非对话开始时静态合并：

```
操作文件 F = src/core/parser.py

解析过程：
  1. 确定 F 的物理路径
  2. 从 F 所在目录向上遍历至仓库根
  3. 收集路径上所有 AGENTS.md（不在路径上的不解析）
  4. 按深度排序（浅→深）
  5. 应用覆盖规则：深层的同名规则覆盖浅层
  6. 叠加对话中直接指令（最高优先级）
```

**路径切换影响：** CWD = src/core/ → 读 src/core/AGENTS.md + 根 AGENTS.md；CWD = src/utils/ → 不读 src/core/AGENTS.md。不是全量注入再过滤，是路径感知的实时解析。

#### 7.2 规则冲突消解矩阵

| 规则来源 | 根 AGENTS.md | 中层 AGENTS.md | 深层 AGENTS.md | 对话指令 |
|----------|-------------|----------------|----------------|----------|
| **根 AGENTS.md** | — | 被覆盖 | 被覆盖 | 被覆盖 |
| **中层 AGENTS.md** | 可覆盖根 | — | 被覆盖 | 被覆盖 |
| **深层 AGENTS.md** | 可覆盖根/中层 | 可覆盖中层 | — | 被覆盖 |
| **对话指令** | 覆盖一切 | 覆盖一切 | 覆盖一切 | — |

**设计意图：** 与 Git .gitignore 同构——深层目录允许对全局规则设置局部例外。大型项目中不同模块有不同约束，强行统一规则会阻塞局部最优。

### 8. 工具调用结果的注入与截断策略

#### 8.1 截断阈值（分级降级而非一刀切）

| 输出量级 | 处理方式 | 对推理的影响 |
|----------|----------|-------------|
| <1KB | 完整保留，直接注入 | 直接可用 |
| 1-50KB | 保留但注意力优先级降级 | "有这些信息，但不会给满注意力" |
| 50KB-1MB | 截断 + 标记 `[truncated...]` | 必须重新定向查询获得完整内容 |
| >1MB | 严重截断或完全丢弃 | 工具调用相当于没发生 |

**关键：** Agent 在接收结果时就已经"感知"了截断，并在推理中主动标记"这个结果不完整，需要重新查询"。

#### 8.2 五重信息密度优化策略

| # | 策略 | 行为示例 | 原理 |
|---|------|----------|------|
| 1 | 精准搜索 | `rg 'def handle_' src/` 而非 `grep -r .` | 减少噪音，提高信噪比 |
| 2 | 渐进式探索 | 先 ls → 再 cat 具体文件 | 避免一次加载过多无关文件 |
| 3 | git 辅助 | `git log --oneline -5` 而非完整 log | 时间线摘要优于全量历史 |
| 4 | **差分覆盖** | 第一次 rg 'def ' → 第二次 rg 'def handle_' | 每次在前一次结果上缩小范围 |
| 5 | **信任工具** | apply_patch 后不 re-read | 工具结果已包含成功/失败信息 |

**差分覆盖（Delta Coverage）** 是关键新策略：每次后续调用都在前一次结果的基础上缩小范围，逐步提高信噪比，而非每次都从全量探索开始。

### 9. 从诊断到验证的完整交互时序（注意力流视角）

完整的 3 阶段、8 步注意力流演化，详见 `references/interaction-sequence.md`。

**三个关键修正（推演框架的核心）：**

#### 9.1 修正 1：Agent 不是"选择"诊断——注意力流自然导向

```
你看到的：Agent 理性选择了"先诊断再修改"
实际发生的：用户"优化" + AGENTS.md"先诊断" + 系统提示词"工具使用"
  → 三者在跨注意力中形成共振
  → 注意力流自然导向"探索"路径
  → 如果用户说"直接改" → 对话指令覆盖 AGENTS.md → 注意力流转向修改
```

**Agent 行为是注意力流自然导航的结果，不是显式决策。**

#### 9.2 修正 2：τ_i ≤ τ_target/N 是注意力约束，不是数值检查

```
正向堆叠时：
  τ_i ≤ τ_target/N 约束Token 在注意力中获得特定权重
  如果修复方案过于复杂（隐含超过 τ_target/N 边界）
  → 约束Token 与修复方案的注意力差异过大
  → Agent"感知"方案不合理 → 主动简化

不是数值比较，是注意力层面的"合理性校验"。
```

#### 9.3 修正 3：效果验证中的偏差分析是跨注意力共振

```
测试结果 "τ_total=18ms" 注入后获得高注意力
早期诊断报告 "τ_target=50ms" 已在上下文中衰减

跨注意力共振：
  "18ms" vs "50ms" → 差异显著 → 强注意力信号 → 自动判断"达成"

但如果诊断报告已接近截断边缘：
  → 共振减弱 → Agent 询问"目标是多少？"
  → 用户回答重新注入 → 形成新共振 → 确认完成
```

### 10. 操作架构原则（Operational Architecture）

Agent 所依赖的核心操作工具的设计原则，映射到韬定律：

| 设计原则 | 对应实现 | 韬定律映射 |
|----------|----------|-----------|
| **最小副作用** | apply_patch 原子性（全或无） | τ_i 局部优化不破坏全局 |
| **状态显式化** | update_plan 状态机 + ls/cat 验证 | 反向诊断"不讲故事，拿数据说话" |
| **约束优于自由** | 单一 in_progress + ≤7 词计划 + 格式规范 | τ_i ≤ τ_target/N 的工程实现 |
| **操作级审批** | 审批粒度 ≤ 副作用产生的最小单元 | 防止"审批一次，执行十次" |

## 注意事项

- 本技能是元认知技能（关于认知的认知），适用于自我诊断和任务规划阶段
- 不要在每个简单任务中都完整使用本技能——仅当任务复杂度显著或出现注意力衰减迹象时
- 与 first-principles-reasoning 结合使用时：先做 ICL 注意力分析（了解自己哪里可能遗忘），再做 FPR 推理（基于准确的信息假设）

- 与前端开发结合使用时：注意力流推演帮助理解"我在探索什么阶段"，避免过早跳入修改
