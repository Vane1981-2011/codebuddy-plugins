# 上下文自动清理协议（Context Cleanup Protocol）

## 核心原则

上下文即成本。每次任务完成后，必须执行三条原则：

1. **写入最小化** —— 记忆文件只存关键结论，不存过程叙述
2. **中间物即焚** —— 临时文件/缓存/构建产物用完即删
3. **输出去冗余** —— 最终回复不重复记忆文件中已有的信息

## 触发条件

以下任一条件满足时，自动加载本协议：

- 任何实质性任务完成（3+ tool calls）后，自动执行清理流程
- 用户明确提及「清理上下文」「释放内存」「降低消耗」「优化 token」「减少积分消耗」
- Unified Bus 路由自动匹配：所有非平凡路由的后置步骤

**不触发**：纯问答/闲聊/单步查询——这些场景无需清理。

---

## 三层清理架构

```
Layer 1 — 写入压缩（每次任务后）
         ├── 日日志：每条任务 ≤ 2 行
         ├── MEMORY.md：仅项目约定/偏好/技术选型
         └── 用户 Memory：仅跨项目通用规则

Layer 2 — 文件即焚（每次任务后）
         ├── 检查 workdir 下的临时文件
         ├── 删除中间产物（build cache / temp / *.tmp）
         └── 保留最终交付物

Layer 3 — 定期蒸馏（每周自动）
         ├── 扫描 > 30 天的日日志
         ├── 提取关键内容 → 追加到 MEMORY.md 按主题归类
         └── 删除已蒸馏的日日志文件
```

---

## Layer 1 — 写入压缩协议

### 1.1 日日志压缩规则

写入 `{workspace}/.workbuddy/memory/YYYY-MM-DD.md` 时：

| 规则 | 说明 |
|------|------|
| **一行一任务** | 每个实质性任务不超过 2 行，使用 `-` 前缀 + 关键词 |
| **禁止** | 过程叙述、中间结果、错误重试细节、工具调用日志 |
| **允许** | 最终决策、产出文件路径、关键技术选型、重要约定 |
| **格式** | `- [分类] 关键内容 —— 产出物路径` |

**对比示例：**

```
❌ 禁止（冗余记录）：
今天我帮用户创建了一个 HTML 页面，用于展示数据分析结果。
首先我创建了 index.html 文件，然后添加了 CSS 样式...
中间遇到了一个 JavaScript 错误，我修复了它...
最终用户对结果表示满意。

✅ 规范（压缩记录）：
- [Web] 数据分析看板 —— index.html, chart.js 集成
- [决策] Chart.js 选型，放弃 ECharts（体积过大）
```

### 1.2 MEMORY.md 写入规则

写入 `{workspace}/.workbuddy/memory/MEMORY.md` 时：

| 应写入 | 不应写入 |
|--------|----------|
| 项目约定（框架/库/部署方式） | 单次任务日志 |
| 用户偏好（风格/命名/工具链） | 临时配置/调试信息 |
| 技术选型及理由 | 已完成的一次性操作 |
| 重要决策和约束条件 | 错误日志和排查过程 |

### 1.3 用户级 Memory 写入规则

写入 `~/.workbuddy/MEMORY.md` 时：

| 应写入 | 不应写入 |
|--------|----------|
| 跨项目通用偏好/习惯 | 单项目特定约定 |
| 用户个人设置规则 | 临时偏好/实验性规则 |

## Layer 2 — 文件即焚协议

### 2.1 自动检查清单

任务完成后，逐项检查当前工作目录：

| 检查项 | 操作 |
|--------|------|
| `node_modules/` | 保留（可重建）——不删除 |
| `dist/` / `build/` | 交付物已部署则删除；否则保留 |
| `*.tmp` / `*.log` / `.cache/` | **立即删除** |
| `__pycache__/` / `*.pyc` | **立即删除** |
| 中间处理文件 | 已合并到最终产出的中间文件 **立即删除** |
| 重复/旧版本 | 保留最新版本，删除旧版 |

### 2.2 安全红线

**以下文件/目录绝不可删除：**

- `.workbuddy/` 目录及所有子文件
- `~/.workbuddy/` 目录及所有子文件
- 用户明确指定的最终交付物
- 桌面/下载/文档等个人目录下的文件

---

## Layer 3 — 定期蒸馏协议

每周执行一次（通过 Automation 自动触发）：

1. 扫描 `{workspace}/.workbuddy/memory/` 下所有 `*.md` 文件
2. 筛选文件名日期 > 30 天的文件
3. 提取每个文件中的关键内容
4. 按主题归类后追加到 `MEMORY.md`
5. 删除已蒸馏的日日志文件
6. 输出蒸馏报告：处理了 N 个文件，提取了 M 条关键信息

**蒸馏判断标准：**

| 保留 | 丢弃 |
|------|------|
| 项目约定/技术决策 | 单次操作日志 |
| 用户偏好/习惯 | 已完成的任务记录 |
| 错误模式和解决方案（泛化后） | 特定于某次任务的上下文 |
| 可复用的架构设计 | 过时的信息 |

## 执行流程

### 标准执行（每次任务完成后）

```
任务完成
    │
    ├─→ Step 1: 上下文审计
    │    ├── 识别本任务产出（文件/决策/配置）
    │    ├── 标记「需持久化」vs「临时中间物」
    │    └── 检查是否有冗余输出文件
    │
    ├─→ Step 2: 写入压缩
    │    ├── 日日志写入（≤2行/任务）
    │    ├── MEMORY.md 更新（如有新约定/偏好）
    │    └── 用户 Memory 更新（如涉及跨项目规则）
    │
    ├─→ Step 3: 文件即焚
    │    ├── 删除临时文件/缓存
    │    └── 清理中间产物
    │
    └─→ Step 4: 自我审查
         ├── 最终回复是否包含冗余信息？
         ├── 是否有信息已在记忆文件中？
         └── 是 → 精简回复；否 → 正常输出
```

### 手动触发执行

当用户说「清理上下文」时：

1. 检查当前会话产出的文件
2. 执行 Layer 2 文件即焚
3. 确认 Layer 1 记忆写入已压缩
4. 输出清理报告：「已清理 X 个临时文件，释放 Y KB，记忆压缩率 Z%」

## Token 优化检查表

在每次回复用户之前，执行以下自检：

- [ ] 回复中是否重复了记忆文件中已有的信息？→ 删除
- [ ] 回复中是否包含中间过程/调试信息？→ 删除
- [ ] 是否创建了不必要的文件？→ 删除
- [ ] 文件路径是否简洁（使用相对路径）？→ 修正
- [ ] 代码注释是否仅包含关键逻辑？→ 精简

## 自动化配置

本协议建议配置两项自动化：

### 自动化 1：每周记忆蒸馏

- **频率**：每周日 02:00
- **操作**：蒸馏 >30 天的日日志到 MEMORY.md
- **RRULE**：`FREQ=WEEKLY;BYDAY=SU;BYHOUR=2`

### 自动化 2：每日上下文审查

- **频率**：每日 23:00
- **操作**：检查当日记忆写入是否符合压缩规则
- **RRULE**：`FREQ=DAILY;BYHOUR=23`
